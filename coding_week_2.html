Beat One · Lesson 1 — From Script to App

When a Script Isn't Enough — Meet the Four Parts of an App

Maya's receipt script was a private tool: she typed a command, it printed a number, done. An app is different — other people use it, from their own devices, and it has to remember things between visits. That means four moving parts working together: an interface people see, logic that does the work, data that's stored, and state — what's true right now. Today Maya decides ShiftSwap is worth building as a real app, not another lonely script.

📖 The story so far Sunday, 8:10 p.m. A helper texts: "Can't do Saturday's market — anyone cover?" Three replies land, two helpers, and nobody's sure who answered first. Maya almost writes another little script to log it. Then she catches herself: a script that only runs on my laptop can't help two people on their phones on a Saturday morning. This isn't a script problem — it's an app problem. But before she builds anything, she has to choose the right path.

Beat Two · Lesson 2 — Design First

Design Before You Build — Screens, a User Story, and a Data Sketch

The biggest beginner trap is building before you know what you're building. Maya spends one evening with pen and paper first: what screens exist, how a person moves between them, the one-sentence user story that defines "done," and a rough sketch of what data gets stored. Fifteen minutes of design saves hours of rebuilding.

📖 The story so far Monday evening. Path chosen: a small ShiftSwap app. Before a single line of code, Maya sketches. She draws three boxes — a Shift List, an Add-Shift form, and a confirmation — and draws arrows for how a helper moves between them. Then she writes one sentence that decides everything the app must (and must not) do. Design is cheap on paper and expensive in code.
🔍 Maya's notebook — a user story vs. a vague wish

A user story is one sentence: "As a [who], I want to [do what], so that [why]." It's the smallest complete definition of a feature. Vague wishes ("make it nice") can't be built or checked; a user story can — it tells you exactly what to build and how to know it works.

💚 Stories you can actually build
  • "As a helper, I want to see the open shifts, so that I know what's free."
  • "As a helper, I want to claim an open shift, so that the others know it's covered."
  • "As Maya, I want to post a shift I can't make, so that someone can pick it up."
💔 Wishes that build nothing
  • "Make it modern and clean" → a taste, not a task — unbuildable
  • "Handle everything about scheduling" → infinite scope, never done
  • "It should just work" → defines nothing to build or test

Beat Two · Lesson 2 continued — Cut Scope, Sketch the Data

Design isn't just adding ideas — it's the discipline of removing them. Maya lists everything ShiftSwap could do, then ruthlessly cuts anything that isn't essential to the one user story. What survives is the MVP: the smallest version that's genuinely useful. The rest goes on a "someday" list, not into this weekend.

Beat Three · Lesson 3 — Build It

Build One Screen at a Time — Wire Interface to Logic to Data

Now Maya builds — but not all at once. She picks a low-friction approach (an AI builder that shows a live preview in the browser, nothing to install), then grows the app one screen at a time: get the list showing, then the Claim button working, then saving. Each small piece is tested before the next is added. An app is assembled, not summoned.

Beat Three · Lesson 3 continued — The Cross-Layer Bug

The Data Vanishes on Refresh — Debug Across the Layers

Real apps break at the seams between parts — where the interface hands off to logic, or logic to data. Maya hits the classic beginner bug: everything works until she refreshes the page, and every shift disappears. The fix isn't in the screen she's staring at; it's one layer down. Debugging an app means finding which layer actually failed.

📖 The story so far Wednesday, late. ShiftSwap looks finished: Maya posts a shift, claims one, it all works. Then she presses refresh to check — and the list is empty. Every shift gone. Her Week-1 instinct kicks in: don't panic, read what's happening. The interface is fine, the logic is fine — so the problem must live in the layer that's supposed to remember. Work through the wiring checklist, then diagnose the bug.

Trace the layers (click each step)

  • Confirm the interface shows shifts from the data, not a fixed list in the code
  • Trace a Claim click: interface → logic → update the data
  • Reproduce the bug on purpose: add a shift, refresh, watch it vanish
  • Ask the AI, with context: "shifts disappear on refresh — where are they stored?"
  • Fix it: save shifts to the browser's storage, load them on start-up
  • Re-test: add a shift, refresh — it's still there. Bug closed.
🔧 Cross-layer bug fixed. The data now lives in storage, not just in memory — so a refresh no longer wipes it. Maya can explain exactly which layer failed and why.

Beat Four · Lesson 4 — Test, Ship & Iterate

Test the Sad Paths, Ship to a URL, Then Trust-Check the Code

A build that works for you isn't shipped. Maya tests the happy path and the sad ones (what if a helper leaves a field blank? types nonsense?), deploys ShiftSwap to a real URL a teammate can open, gets first-user feedback — and does a trust-check on the AI's code before she relies on it. Three things got flagged. For each, she decides: Ship it, Verify it, or Block & fix.

📖 The story so far Thursday night. ShiftSwap survives a refresh, so Maya sends the link to one helper — the first real user who isn't her. Within minutes it breaks in a way she never tried: the helper pressed Post with the date left blank, and the app threw an error. Good — that's exactly what testing before a wide launch is for. She adds a check that catches the blank field with a friendly message, then runs a final trust-check on the AI's code, the way a professional reviews a pull request. Three items sit in front of her. Judge each: Ship (verified good), Verify (one quick check first), or Block & fix (a real problem to fix before shipping).

Lesson 1

From Script to App

A script runs for you; an app runs for other people and remembers things. Every app is four parts — interface, logic, data, state. Knowing when you've outgrown a script is the first move. Beat 1.

Lesson 2

Design First

Sketch the screens and the flow, write a one-sentence user story, sketch the data — then cut scope hard to a finishable MVP. Fifteen minutes on paper saves hours in code. Beat 2.

Lesson 3

Build It

Pick a low-friction builder, grow the app one screen at a time, and wire interface → logic → data. When a bug crosses layers (the data vanished on refresh), find which layer actually failed. Beat 3.

Lesson 4

Test, Ship & Iterate

Test the happy and sad paths, handle the user who types something weird, deploy to a real URL, gather first-user feedback, and trust-check the AI's code — catch the hallucinated library, never ship a hard-coded secret. Then document and ship. Beat 4.

ShiftSwap is a teaching scenario.
