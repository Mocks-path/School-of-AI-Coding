Week 1 · Lesson 04 · AI Programming

From script to shipped: the last mile.

You can make code run. Now comes the part that separates "I wrote a thing" from "I built something people can rely on": giving your work save-points so mistakes aren't fatal, proving it actually works, and knowing when to trust AI-written code versus when to check it yourself. Fair warning — the last mile is where careless builders ship bugs they can't undo.

01 / 04

The maturity ladder: script → tool → product

Not everything you build needs to become a "product." Most things start — and should stay — as a quick script. The skill is knowing which rung a piece of work belongs on, because each rung costs more effort and buys more reliability.

A script is a one-off: it does a job once, for you, then you move on. It doesn't need saving, testing, or polish — it needs to run correctly this one time. A tool is a script you'll reuse: now it deserves save-points, a clear name, and a note on how to run it, because future-you will forget. A product is something other people depend on: now it needs real testing, guardrails against bad input, and a way to fix it safely after it's out. Climbing a rung isn't automatic virtue — over-building a one-off wastes your time as surely as under-building a product burns your users. Walk the ladder below and answer honestly.

The one mistake this ladder prevents

Beginners do both wrong directions: they spend a weekend hardening a script they'll run once, and they ship a thing others depend on with zero tests and no save-points. Match the effort to the rung. If getting it wrong costs nothing and nobody else runs it, "make it run and move on" is the correct, mature choice — not laziness.

02 / 04

Version control: save-points for your code

Version control sounds technical, but the idea is a video game: it lets you save your progress at any point and reload an earlier save if you mess up. Each save is a "commit" — a labelled snapshot of your whole project you can always return to.

The single most freeing fact about building software: with save-points, no mistake is permanent. Delete the wrong thing, break something that worked yesterday, chase a bad idea for an hour — you can roll back to any earlier commit and it's as if it never happened. That safety net is what turns "I'm scared to change this working code" into "let me just try it and see."

Beyond saving, version control gives you a timeline: a readable history of every change, when you made it, and a short note on why. And it gives you branches — a way to try a risky idea on a copy of the project, off to the side, so your working version stays untouched until you're sure. If the experiment fails, you throw the branch away; if it works, you merge it back in.

How to actually use this as a beginner

You don't need to master every command to get the whole benefit. Adopt one habit: commit every time something works. Made the login screen appear? Save-point. Fixed a bug? That single discipline means you're never more than one small step from a version that ran — and AI can help you write clear commit notes and even explain what changed between two save-points.

03 / 04

Testing: how you actually KNOW it works

"It ran without an error" and "it works" are different claims. A program can run perfectly and still give the wrong answer. Testing is simply the discipline of checking the output against what you already know the right answer should be.

Here's the trap: you run your program, no red text appears, and you declare victory. But no error just means nothing crashed — it says nothing about whether the result is correct. The only way to know is to feed it a case where you already know the answer and confirm it matches. Average of 5 and 3? You know it's 4. If the program says 4, that path works. If it says 2.67, you found a bug the error messages would never have caught.

Good testers don't just try the easy case — they hunt the edge cases: the empty input, the zero, the huge number, the unexpected type. That's where programs quietly break. And this is a place AI genuinely helps: ask it to list the tricky cases you should check, or to write small tests that prove each one. But you still read the results — a test that passes for the wrong reason is worse than no test.

04 / 04

The trust-vs-verify checklist for AI code

AI writes plausible code fast — and plausible is not the same as correct. Before you run anything AI hands you, run it past this checklist. Some green flags let you trust and go; some red flags mean stop and verify, every time.

Set the expectation first: AI is a fast, confident junior developer who never says "I'm not sure." Most of what it writes is fine. But it will occasionally invent a library that doesn't exist, paste a secret key in plain sight, suggest a command that deletes more than you meant, or ignore the exact edge case that matters. Your job isn't to distrust everything — it's to know which specific things always deserve a second look.

Click any item to expand it. Green items are the reassuring signs; red items are the ones that should make you pause before you run a single line.

Figure 4 · Green flags & red flags for AI code
Green

You understand what every line does

▸
  • You can explain the code back in your own words
  • Nothing in it is "magic you'll trust blindly"
  • If it broke, you'd know roughly where to look
Why it's green

Code you understand is code you can fix, test, and defend. Ask AI to add a short comment to any line you can't explain — then read it.

Trust level

Trust and run — but still test the output against a known answer.

Green

It uses well-known, real libraries

▸
  • The imported tools are ones you can look up and find widely used
  • The install command actually finds the package
  • The function names match the real documentation
Why it's green

Popular, real libraries mean answers, examples, and safety in numbers. If you've never heard of one, that's your cue to verify it exists before trusting it.

Trust level

Trust — after a five-second check that the library is real and current.

Green

It runs, and you tested a hard case

▸
  • No errors AND correct output on a case you know
  • You tried at least one edge case, not just the easy one
  • You have a save-point you can roll back to
Why it's green

Verified behaviour plus a save-point is the strongest position you can be in. This is "trust" earned honestly, not assumed.

Trust level

Trust fully — you've done the work to earn it.

Red

Hallucinated library or function

▸
  • An import you can't find anywhere when you search for it
  • A function that "sounds right" but isn't in the real docs
  • An install command that fails to find the package
Why it's red

AI sometimes invents plausible-sounding packages and methods. If you can't find it in the real documentation, it may not exist — don't build on a ghost.

Verify

Look it up before you trust it. If it's not real, ask AI for the actual, documented way.

Red

Secrets or keys sitting in the code

▸
  • An API key, password, or token pasted directly into a file
  • A "put your secret here" line you're about to save publicly
  • Any credential that would leak if you shared the code
Why it's red

A secret committed to a save-point or shared online can be scraped and abused within minutes. AI often inlines them for a "working" demo — never ship that.

Verify

Move every secret out of the code before committing. Ask AI how to load it safely from outside the file.

Red

Dangerous or irreversible commands

▸
  • Anything that deletes, overwrites, or force-removes files
  • Commands that move money, send messages, or change live data
  • A "just run this to fix it" line you don't fully understand
Why it's red

Some actions can't be undone — and AI can suggest a broad delete when you asked for a narrow one. A save-point protects code, not the outside world.

Verify

Read every destructive command line by line. Do a dry run first. Never paste-and-run something you can't explain.

Red

Edge cases quietly ignored

▸
  • No handling for empty input, zero, or a missing value
  • Works on the neat example but not the messy real one
  • Assumes input is always well-formed — it won't be
Why it's red

AI optimises for the happy path you described. The blank field, the huge number, the wrong type — those are where real programs break in front of real people.

Verify

Ask AI to list the edge cases it didn't handle, then test each one yourself before you trust the result.

What "shipping responsibly" really looks like

A genuinely good ship: you understood every line, confirmed the libraries were real, pulled the one secret out of the code, read the delete command twice, tested the empty-input case, and committed a save-point before flipping it on. That's maybe ten extra minutes. It's the difference between "the AI wrote it, so I hope it's fine" and "I verified it, so I know it is." Trust is fine — verify first.

What to carry forward

Running code is the start of the last mile, not the end. Match your effort to the rung — script, tool, or product. Commit a save-point every time something works, so no mistake is permanent. Prove it works by testing against known answers and hunting edge cases. And treat AI code as a fast junior: trust the green flags, verify the red ones, every time.

  • Script → tool → product: build to the rung, don't over- or under-build
  • Version control = save-points; commit every time something works
  • "It ran" ≠ "it works" — test output against answers you already know
  • Hunt edge cases: empty input, zero, huge numbers, wrong types
  • AI red flags: fake libraries, secrets in code, dangerous commands, skipped edges
