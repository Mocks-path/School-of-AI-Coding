Week 5 · Lesson 03 · AI APIs

Your code just asked another program for help.

An API call is one program asking another to do something and hand back the result — fetch some data, run a model, send a message. Making a single call is the easy part. The real skill is orchestrating many of them: choosing the right approach for the job, chaining one call's output into the next call's input, insisting on structured results you can actually trust, and staying standing when a call inevitably fails. This lesson turns "I can make an API call" into "I can build a small, reliable system out of them."

01 / 04

Chaining: one call's output feeds the next

Real work is almost never a single request. You fetch something, hand it to an AI model, reshape the result, then send it somewhere. Each call takes the previous call's output as its input — that hand-off is the whole idea. Press play and watch a four-step chain execute, step by step.

A chain is just plumbing you can reason about. The trick is that the pieces only fit if each step produces exactly what the next step expects. If the fetch returns messy text, the summarize step chokes; if the summary isn't structured, the formatter can't lay it out. So you design the chain backwards from the delivery: what does the final step need, and what must each earlier step hand it? Build it that way and a complicated task becomes four small, testable calls instead of one tangled mess. Watch this chain run — raw data in, a finished message out.

Design backwards, build forwards

Notice each step does one job and hands off cleanly. That is what makes a chain debuggable: when the final message looks wrong, you can inspect the output of each call and find exactly where it broke, instead of staring at one giant black box. Keep the steps small, name what each one returns, and a chain becomes something you can grow — add a translate step, swap the source, insert a check — without rewriting the whole thing.

02 / 04

Ask for structure — then check it

If a call returns a wall of free text, your next step has to guess where the useful bits are. So don't accept prose you have to untangle by hand — ask the model for named fields in a known shape, then validate that shape before you trust it. Click each response to see what passed, what failed, and what to do about it.

Asking for structured output means telling the model up front: "return an object with these exact fields and these types." Most modern APIs can even enforce that shape for you. But asking is a promise, not a guarantee — a model can still drop a field, put text where you wanted a number, or ignore the format entirely on a bad day. That's why the second half matters as much as the first: validate the response against what you expected, and decide in advance what happens when it doesn't match. A pipeline that assumes the shape is always perfect is a pipeline that breaks silently. Click each of the four responses below.

Structure is a promise you still verify

The habit to build: never let an AI response flow into the next step unchecked. A tiny validation — "are all the fields here, are the types right, are the values in range?" — turns a fragile pipeline into a sturdy one. When the check fails, you already know the move: supply a default, coerce the value, or reject and retry. That single guard is the difference between a demo that works once and a system you can leave running.

03 / 04

Every call can fail — plan for it

Networks time out. Providers get overloaded and push back with a rate limit. Models occasionally return junk. None of this is exotic — it's the normal weather of calling other people's servers. The question is never "will a call fail?" but "what happens when it does?" Toggle the failure modes and watch the exposure climb, and the recommended handling change.

There's a simple ladder of defence, and you climb it as the risk rises. For a rare, transient glitch, you retry with backoff — wait a moment and try again, doubling the wait each time so you don't hammer a struggling server. When retries aren't enough, you add a fallback — a smaller model, a cached answer, or a simpler path that still gets the user something. And underneath it all sits a fail-safe: a graceful default so that even when everything goes wrong, the user sees a calm message instead of a broken screen. Retry, then fall back, then fail safe

Order matters. Reach for the cheapest fix first — a retry with backoff clears most transient failures on its own. Escalate to a fallback only when retries won't help, and always leave a fail-safe underneath so nothing the user sees is ever just "broken." This isn't defensive paranoia; it's the difference between a script that works on your machine at 2pm and a system that keeps working at 3am when a server you don't control is having a bad night.

04 / 04

Do you even need to write the code?

Before you write a single line, ask the honest question: what's the cheapest way to solve this that will actually hold up? Sometimes it's a no-code tool. Sometimes it's a raw API call you control completely. Most often it's somewhere in between. Click each approach to see where it sits on the map of control versus effort — and when it's the right call.

There's no "best" way to put an AI model to work; there's only the right trade-off for this job. A no-code tool gets you running in minutes but boxes you into what it exposes. A direct API call gives you total control but you own every detail, including the failures from the last three sections. Automation platforms and frameworks live in the middle, trading some control for a lot less plumbing. Buy, wire, or build — pick on purpose

The mistake is defaulting: some people write code for everything, others refuse to ever leave the no-code box. Neither is a strategy. The move is to name the job, ask how much control it truly needs and how long it has to last, and pick the lowest-effort approach that clears that bar. Prototype in no-code, graduate to a direct call when you outgrow it, reach for a framework when it has to grow. Same judgment as everything else in this course: match the tool to the problem, not to the hype.

What to carry forward

An API call is a small thing; a system made of them is where the value is. Chain calls so each output feeds the next, and design the chain backwards from what you need to deliver. Ask for structured output and always validate it before you trust it. Assume every call can fail, and climb the resilience ladder — retry, fall back, fail safe. And before you write anything, choose your approach on purpose: no-code, direct API, or somewhere in between, matched to the job.

  • Chain calls so one's output is the next one's input — small, testable steps
  • Ask for named fields in a known shape, then validate before you trust
  • When validation fails: supply a default, coerce, or reject and re-ask
  • Every call can fail — retry with backoff, then fallback, then fail safe
  • No-code vs direct API is a trade-off of control against effort — pick on purpose
