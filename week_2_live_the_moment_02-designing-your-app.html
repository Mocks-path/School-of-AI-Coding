Designing the App Before You Build — think first, build fast

Four hands-on activities. Put the screens of a user flow in order, build a clear user story block by block, learn the plain-English words for how data fits together, and decide which features belong in the first version. Because building is now fast, thinking is where your leverage is — five minutes of design saves an hour of AI building the wrong thing.

Order the screens of a user flow

Before you build a screen, you map the flow — the path a user walks from “I want to do this” to “done”. A good flow has four beats: an ENTRY (where they start), the ACTION (what they do), a CONFIRM (the app checks & agrees), and an END (they see it worked). Must-have or nice-to-have? — scope the first version

The number-one reason beginner apps never get finished is trying to build everything at once. The cure is the MVP — the smallest version that actually solves the core problem. Sort each proposed feature for our badminton-booking app into must-have (the app is useless without it), nice-to-have (great later), or not now (a whole different project). Wrong answers carry a hover hint.

M1

Must-have (MVP)

Remove it and the app can’t do its one core job. This is the shortlist you build first.

  • See available slots
  • Book a slot
  • Save that booking so it’s not double-booked
N2

Nice-to-have

Genuinely useful, but the app still works without it. Add it once the core is solid.

  • A reminder email the day before
  • A profile photo for each player
  • Dark mode
X3

Not now

A different app in disguise — huge scope for a first build. Note it, park it.

  • In-app payments & refunds
  • A social feed for players
  • Multi-city franchise support
💡 The MVP question for every feature: “If this were missing, could a user still do the one thing this app exists for?” If yes, it’s not a must-have — no matter how nice it sounds. Ruthless scoping is what gets a first version finished instead of endlessly “almost ready.”

Build the user story — role, goal, reason

A user story is the one-sentence recipe designers use to keep a feature honest: “As a [role], I want to [goal], so that [reason].” It names who it’s for, what they do, and why they care — and nothing else. Data words & right-sized scope — the design quiz

Two things separate a plan that builds smoothly from one that stalls: knowing the plain-English words for your data model (entity, field, relationship), and scoping the first version so it’s actually finishable.
