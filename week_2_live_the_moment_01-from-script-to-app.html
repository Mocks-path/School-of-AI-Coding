The four parts of any app

Whether it’s a to-do list or a banking app, every app is built from the same four kinds of parts. The interface is what the user sees and touches. The logic is the rules that decide what happens. The data is the information that gets saved. The state is what’s true right now in this session. Study the four, then drag each real example into the part it belongs to. Guess freely — every card carries a hover hint with the answer.

UI

Interface

What the user sees and touches — buttons, forms, lists, screens. The visible surface of the app.

+ Buttons, text boxes, menus, the layout + Everything on screen the user interacts with − Not where decisions or storage happen
LG

Logic

The rules and decisions: “if the field is empty, show a warning.” The thinking behind the buttons.

+ Validation, calculations, if-this-then-that + Turns a click into an actual action − Invisible to the user — it just runs
DB

Data

The information that gets saved and comes back later — accounts, entries, records. Survives a refresh.

+ Anything stored: users, posts, orders + Still there when you close and reopen − Not the screen and not the rules
ST

State

What’s true right now in this session — who’s logged in, which tab is open, is it still loading.

+ “Logged in”, “loading”, “dark mode on” + The app’s current, temporary situation − Often resets when the session ends
💡 The core question for every piece of an app: “Is this what the user sees (interface), a rule (logic), something saved (data), or just what’s true this second (state)?” Almost every feature you’ll ever describe to an AI breaks down into these four. Naming the part first makes your request precise — and precise requests get better software.

Does this even need an app?

The most useful decision a builder makes is before building: not every problem needs a full app. A one-off task might just need a script. Tracking a list might be fine in a spreadsheet. Something that runs on a schedule might be an automation. An app earns its keep only when several people need a shared interface, saved data, and rules that live on. Read the scenario below, then pick the right-sized tool.

📝 The scenario: Priya volunteers at a small community library. Twelve volunteers, working different shifts from their own phones, all need to check out books to members, see who has what right now, and keep that record accurate over the long term. Today they scribble it in a shared notebook and things get lost.

💡 The honest takeaway: AI genuinely collapses the time to a first working version from weeks to an afternoon — that part is real, not hype. What it does not collapse is the work of making an app reliable, safe, and pleasant to use for twelve real volunteers. A fast demo is the start of the job, not the end of it — which is exactly the myth the next section takes apart.
