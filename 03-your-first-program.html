Week 1 · Lesson 03 · AI Programming

Your first program will break. That's the point.

The gap between "I typed some code" and "I built something that runs" is one skill: reading what the computer tells you when it complains. In this lesson we pick a low-friction place to write code, run the build loop until it works, decode an error message word by word, debug alongside AI, and ship one small working thing.

01 / 04

Start where there's nothing to install

Beginners quit in the first hour — not because coding is hard, but because setup is. Wrong version, missing path, a cryptic install error before you've written a single line. The fix is to start somewhere the environment already exists and just works.

You do not need to configure a machine to write your first program. Three categories of low-friction environment let you skip setup entirely. A browser sandbox runs code on a webpage — nothing to download, just type and press run. A notebook lets you write code in small cells and see the result of each one right below it, which is perfect for learning because you get feedback in tiny steps. A cloud IDE gives you a full code editor in your browser, pre-loaded with everything, so your project lives online and opens the same on any device.

All three share one virtue: you write code and see it run in the same window, in seconds. That tight loop — type, run, look — is the entire job for now. Later you may install tools on your own machine, but nothing about learning to program requires it today. An error message looks like a wall of scary red text, but it's actually a labelled report telling you exactly what broke and where. Click a dot on the console — or press "Tour all" — to translate each part into plain English.

Tip — read errors bottom-up. The last line names what went wrong; the lines above tell you where. Together they usually point straight at the fix.

The error is on your side

New coders read an error message as "the computer is angry at me." Flip that. An error is the most helpful thing the computer can do — instead of guessing what you meant and doing something wrong silently, it stops and hands you a precise note about what confused it. A program that fails loudly is far easier to fix than one that quietly does the wrong thing. Learn to read these notes and you've learned to program.

02 / 04

Pick your first environment

There are three low-friction ways to write your first program, and they trade convenience against power. Choosing one doesn't lock you in — but it decides how fast you get from "blank screen" to "it ran."

A browser sandbox is a scratchpad: type code, hit run, see output, all on one webpage with zero setup. A notebook is a lab bench: code in cells, results inline, notes alongside — ideal for learning one concept at a time. A cloud IDE is a full workshop: a real editor and project in your browser, closer to how working software is actually built. Each is a legitimate starting point; each has an honest cost. Our honest recommendation

For most beginners: start in a browser sandbox to get the very first "it ran" feeling with zero friction, then move to a notebook the moment you're learning concepts and want to see each step's result. Reach for a cloud IDE only when you're building something with more than one file. Don't let anyone shame you into installing a full toolchain on day one — setup is a skill for later, not a prerequisite for your first program.

03 / 04

Debug with AI — but you steer

Debugging used to mean staring at code and re-reading it until the mistake jumped out. AI collapses that: paste the error, the code, and what you expected versus what you got, and it isolates the likely cause in seconds. Your job shifts from hunting to directing.

Here is what AI genuinely does well when your program breaks: translating error messages into plain English, isolating which line probably caused the failure, proposing a specific fix with an explanation of why, and spotting the class of bug ("this is an off-by-one" / "this variable is the wrong type"). But it only works if you feed it the right three things: the full error, the relevant code, and expected vs. actual behaviour. "It's broken, fix it" gets you a guess; a good report gets you a fix.

And here is the part hype skips: AI is confidently wrong sometimes. It may "fix" the error by deleting the check that caused it, or invent a function that doesn't exist. You stay the pilot: read the explanation, run the change, and confirm the program now does what you actually wanted — not just that the red text disappeared. The report that gets a real fix

Treat AI like a sharp colleague who can't see your screen. Give it the three things it can't guess: the full error text (copy all of it, not a summary), the code around the failing line, and expected vs. got ("I expected it to print the total; it crashed instead"). Ten seconds of good reporting turns a vague back-and-forth into one clean answer — and, quietly, teaches you to read your own bugs.

04 / 04

The build loop, and one small program

Working software isn't written in one heroic pass — it's grown in tiny cycles. Write a little, run it, read what happened, adjust. Each pass through this loop adds one working piece, and the program takes shape under your hands.

Every builder runs the same loop, whether it's their first program or their thousandth: write a small change, run it, read the output or error, fix what's off, and repeat until it does the job. The trick is keeping each pass small — change one thing, then run — so when something breaks, you know exactly what caused it. The loop, in the order to run it

Start by writing the smallest thing that could run — even one line that prints something. Run it immediately; never write three changes before running. When you add the next piece and it breaks, read the error carefully before touching anything. Fix exactly what the message pointed at, then run again to confirm. Finally, verify against a case you didn't build for — an empty name, a weird age — because "it ran once" and "it works" are different claims. None of these steps is glamorous. Together they are how every program you'll ever build gets made.

What to carry forward

You now know what your first program is for. It is not a test you pass or fail — it is a loop you run. You start where there's nothing to install, you write and run in tiny steps, errors are labelled reports on your side, AI helps you decode and fix them while you steer, and "it works" is something you verify, not assume.

  • Start setup-free — a sandbox, notebook, or cloud IDE beats a broken install
  • Errors are helpful reports: read bottom-up for what broke, then where
  • Debug with AI by feeding it the full error, the code, and expected vs. got
  • AI drafts fixes; you run them and confirm the behaviour, not just the silence
  • Run the build loop small: write, run, read, fix, repeat — then verify a hard case
