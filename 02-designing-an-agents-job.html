Designing an agent's job.

An agent is only as good as the job you hand it. In the last lesson we took an agent apart; now we do the harder, more useful thing — write its brief. That means stating the goal, choosing the tools it may reach for, giving it a role, and above all building the guardrails that decide how much it can do on its own and where a human must step in. Get the brief right and an agent is a quiet, reliable helper. Get it vague and it will confidently do the wrong thing at full speed.

01 / 04

A good brief has a small number of parts

Handing an agent a job is like briefing a brand-new assistant on their first day: you say what you want done, who they should be, what they're allowed to touch, and when they must stop and check with you. Miss any one and the day goes sideways.

Newcomers tend to write agent briefs the way they'd type a quick chat message — one vague line and a hope. But an agent will actually go and do things, so the brief carries more weight than a chat prompt ever did. A complete brief names the goal, gives the agent its inputs, sets a role, states the few instructions that matter, lists the exact tools, and — most importantly — builds the guardrails. The brief is where safety is actually decided

Here's the part beginners find surprising: almost everything that makes an agent safe or dangerous is decided in the brief, before it takes a single step. A tool you don't list is an action it can never take. A confirmation gate you add is a mistake it can never make alone. A clear goal is a wrong turn it never takes. You don't supervise an agent mainly by watching it run — you supervise it by writing a careful brief up front. The rest of this lesson zooms into the three parts that matter most: the goal, the tools, and the guardrails.

02 / 04

From a vague wish to a real goal

The most common way an agent goes wrong isn't a bug — it's a fuzzy goal. "Sort out my inbox" means five different things to five people, and the agent has to pick one. A sharp goal removes the guessing. Watch a weak brief become a strong one.

The "before" below is how most people first write a brief: a wish, not an instruction. It sounds clear in your head and means nothing to a machine that has to act on it. The "after" is the same request rewritten as a real goal — an outcome with a finish line, plus the one or two things the agent must never do. The difference is the gap between an agent that quietly saves you an hour and one that sends a half-finished reply to your whole address book. Press Sharpen and watch the brief tighten up.

A goal is an outcome with a fence around it. Notice the sharp brief doesn't just say what to do — it says what to never do ("never send") and when to stop ("after the unread emails"). The "never" list is as important as the "do" list.

The four questions every brief must answer

You don't need a template to write a good brief — you need to answer four questions honestly. What's the goal, stated as a checkable outcome? Who is the agent being asked to be, and how careful? What tools does it get — and, just as important, which does it not? And what are the limits: how many steps, what budget, and which actions must stop for your approval? Answer those four and you've written a brief an agent can run without surprising you. Skip any one and you've left a door open.

03 / 04

The toolbox: what the agent can reach for

An agent's tools are the exact actions it's allowed to take — and the model's clever trick is that it reads the task, then picks the right tool from the box and fills in the details itself. This is called function-calling, and it's easier to watch than to explain. Pick a task below and see which tool the agent reaches for.

Think of the toolbox as a labelled drawer of functions you hand the agent: read_calendar, send_email, query_data, read_file. You don't tell it which to use — you describe the goal, and the model matches the task to a tool and works out the inputs on its own. That matching is the heart of an agent's usefulness, and also exactly why the contents of the box are such a big decision: the agent can only ever do what's in the drawer. Try a few tasks and watch the pick.

Fewer tools, fewer surprises

The instinct is to hand the agent every tool you can "just in case." Resist it. Every tool in the box is one more thing a confused agent can do by mistake, and one more thing you have to trust it with. The durable rule is: give the fewest tools that let it finish the job, and nothing more. An agent that can only read and draft cannot accidentally send, delete, or spend — not because it chose well, but because you never gave it the option. The safest action is the one that was never in the drawer.

04 / 04

Guardrails: how much rope, and where a human stands

The last and most important design decision is autonomy: how much the agent may do on its own versus when it must stop and ask a human. The honest rule is beautifully simple — tie the agent's freedom to how easily a mistake can be undone. Switch between three kinds of action below and watch the verdict change.

Not all actions carry the same risk. Reading a file or searching the web changes nothing, so making the agent ask permission each time just wastes everyone's time. Saving a draft or moving a file changes something, but you can undo it in a click. Sending an email, deleting records, or spending money can't be taken back at all. A good design grants freedom on the harmless end and demands a human "yes" on the dangerous end. Pick an action type below and see how the autonomy call is made.

None of this needs code. The guardrails that matter most are decisions you write into the brief: an allow-list of tools ("only these three"), a step and budget cap ("stop after 20 steps, never spend more than this"), and a confirmation gate ("draft it, then wait for my yes before sending"). Together they mean that even a badly confused agent fails small: it runs out of steps, or hits an action it isn't allowed to take alone, and stops — instead of looping a thousand times or firing off something you can't recall.

The four traps to sidestep

Every part of designing an agent's job has a matching way to get it wrong. Below are the four mistakes beginners make most often. Flip each card to see the trap on the front and the fix on the back — reading them now is far cheaper than learning them from an agent that ran off the rails.

No step cap

The fix

Always set a hard step and budget cap. When it's hit, the agent stops and hands back whatever it has. A bounded failure you can inspect beats an infinite loop you have to kill.

Too many tools
You hand it every tool "just in case," widening what a single wrong step can touch.

The fix

Give the fewest tools the job needs. Every tool you leave out of the box is a whole class of mistake that becomes impossible. Start minimal and add only when a task genuinely needs it.

No confirm gate
The agent can send, delete or pay on its own — and one bad step can't be undone.

The fix

Put a human-in-the-loop gate before anything irreversible. The agent prepares the action and waits for your explicit yes. Keep read-only and easily-undone steps automatic so it stays useful.

"Sort out my inbox" — so the agent guesses your meaning and confidently does the wrong thing.

The fix

Write the goal as a checkable outcome with a clear "done," and state what it must never do. Precise instructions in, sane behaviour out — the agent can only aim at the target you name.

The through-line of every trap

Notice all four traps are the same instinct in different clothes: giving the agent more freedom than the task actually needs. An extra tool, an unbounded loop, a missing gate, a loose goal — each hands the agent room it didn't require and you didn't intend. The discipline of designing an agent's job is subtraction, not addition: the tightest brief that still gets the work done is almost always the safest and the most reliable. You are not limiting the agent for its own sake — you're keeping its power aimed exactly where you want it.

What to carry forward

Designing an agent's job is writing its brief, and the brief is where almost all the safety lives. State the goal as a checkable outcome, give it a role, hand it the fewest tools that finish the work, and set guardrails that match its freedom to how easily a mistake can be undone. A careful brief up front beats anxious watching later — a well-briefed agent is a quiet helper; a vaguely-briefed one is a fast mistake.

  • A brief answers four things: the goal, the role, the tools, the guardrails
  • A real goal is an outcome with a finish line — and a "never do" list
  • Function-calling = the model picks a named tool; you decide which tools exist
  • Give the fewest tools that get the job done — the rest can't go wrong
  • Match autonomy to reversibility: free on read-only, ask before the irreversible
