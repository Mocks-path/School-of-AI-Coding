1

Direct API or no-code tool? — pick the right path

An API is just a way for your build to ask another service to do something. Sometimes you should call it directly in code; often a no-code tool already wraps that same API and hands you the result. Getting this choice right saves days. Study the two paths, then drag each build into where it belongs. Wrong pills carry a hover hint explaining the better home.

💡 The core idea: reach for a good tool when one exists — it's faster and sturdier. Write the API calls yourself when you need control a tool can't give: your own data, custom formatting, unusual chaining, or scale with your own error handling. The skill isn't "always code" or "never code" — it's reading the job.

2

The call failed — now what? Diagnose and fix

Real API calls fail sometimes: the network stalls, you send too fast, or the AI returns something your code can't read. A build that assumes every call works is a build that breaks in front of a user. The skill is recognizing which failure you're seeing and choosing the fix that matches. Read each case and pick the smart move.

3

Ask for structure — match each instruction piece to its job

By default an AI model replies in chatty prose — lovely for humans, useless for code. To use a model inside a build, you tell it to return a predictable structure (like specific fields) so your program can read it every time. A good structured-output instruction is made of parts, each doing a job. Click a piece on the left, then click what it accomplishes. A wrong match shakes red.
