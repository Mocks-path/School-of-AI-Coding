Week 2 · Lesson 03 · AI App Development

An app is just a few working screens — built one at a time.

Last week you learned to describe what you want in plain language and read what AI wrote back. Now you turn that skill into something real: a small app that runs. The secret is that an app isn't one giant thing you build in a heroic sitting — it's a handful of screens, wired to a little logic and a little data, assembled in tiny loops. This lesson shows you the shapes an app is made of, the ways you can build it, and the loop you repeat until it works.

01 / 04

Every app is the same three layers

A first app can feel like magic or mystery — but under the surface, almost every app is built from the same three ideas: a UI (the screen a person sees), some logic (the rules that run when they act), and data (what the app remembers). Once you can point at those three, you can reason about any app you'll ever build.

Beginners often stare at a finished app and feel they could never make one, because they see it all at once. The trick is to stop seeing an app and start seeing its parts. When someone types a task and clicks Add, three things happen in sequence: the UI captures what they typed, the logic decides what to do with it, and the data stores it so it survives. Name the layer, and the problem shrinks

The single most useful habit when building with AI is to describe a change in terms of these three layers. Instead of "the app is broken," you learn to say "the button (UI) runs the add-task rule (logic), but the new task isn't being saved (data)." That precision is what turns AI from a slot machine into a reliable partner — it can fix a clearly-named layer in seconds, but it flails when you hand it a vague "it doesn't work." You supply the diagnosis; AI supplies the fix.

02 / 04

Four ways to build — pick the right one, not the fanciest

There isn't one "correct" way to build an app. There's a spectrum of approaches, from clicking blocks together with no code at all, through AI app builders that write everything from a description, to low-code tools, all the way to hand-guiding a real code framework. Each trades away something to gain something else. The skill isn't knowing the fanciest one — it's matching the approach to what you're actually making.

Here's what beginners get wrong: they reach for the most powerful, code-heavy option because it feels "real," then drown in complexity for an app a no-code tool could have shipped in an afternoon. The right move is the opposite — start as high on the spectrum as your idea allows, and only drop toward code when you hit a wall the simpler tool genuinely can't clear. No approach is "cheating" and none is automatically "better." The best builders move fluidly up and down this spectrum, choosing the least complicated tool that can do the job — and only reaching for code when the simpler options truly can't.

The rule beginners wish they'd known sooner

Start high on the spectrum, drop only when forced. A no-code or AI-builder approach gets a working thing in front of a real person fast, and a rough app you can actually click is worth ten perfect apps still in your head. If you later hit something the tool can't do — a very specific rule, an unusual data shape, a performance need — that's your signal to drop one rung toward code, with AI guiding you through the parts you don't know. You almost never need to start at the bottom.

03 / 04

The build loop: one screen, run, click, fix, commit

Watching an experienced builder work, the surprise is how small each step is. They don't write a whole app and pray. They build one screen, run it immediately, click through it like a suspicious user, fix the first thing that breaks, save the progress, and go around again. That tight loop — not raw talent — is what makes apps actually get finished.

The loop matters because problems caught early are cheap and problems caught late are expensive. If you build ten features and only then run the app, a failure could be hiding in any of the ten, and you're now a detective. If you run after every single change, a new failure can only be in the thing you just touched. AI writes each piece quickly, but you run the loop — you're the one who clicks, notices what's wrong, and decides what to fix next. Step through the loop below.

Build one screen — the loop starts small. You ask AI for a single piece: one screen, one button, one field. Not the whole app — just the next brick. Small changes are easy to check and easy to undo.

Why "commit" is the quiet superpower

Committing means saving a checkpoint of your app the moment it works — a snapshot you can always return to. It sounds boring, but it's what makes bold building safe. Because every working version is saved, you can let AI try something risky on the next turn knowing that if it breaks everything, you rewind to the last good checkpoint and lose nothing. Builders who commit often move faster precisely because they're never afraid to experiment. The loop isn't just build-and-run; it's build, run, and bank the win before reaching for the next one.

04 / 04

Watch one feature come alive: add a task

Let's make the three layers move. A feature isn't real until the whole chain is wired: a person acts on the UI, that triggers some logic, the logic updates the data, and the screen re-draws to show the change. Miss any link and the feature looks done but does nothing. Building is really the craft of completing this chain, one feature at a time.

Take the simplest possible feature: "type a task, click Add, see it appear." It feels like one action, but it's four connected steps, and each must be wired for the whole thing to work. This is exactly where beginners get stuck — the button looks fine, but nothing happens, because one link in the chain was never connected. The order to wire it in

Wire from the action inward. Start with the UI capture — the app must know what the person typed. Connect the button to the logic so a click actually runs something. Write the rule that turns the typed text into a task. Save it to the data so it survives. Re-draw the screen so the person sees it, and clear the box so they can add another. When you ask AI to build a feature, ask for this whole chain at once — "when I click Add, capture the text, add it to the list, show it, and clear the field" — so no link is left dangling.

What to carry forward

You now know what an app is really made of — a UI, some logic, and a little data — and that you build it not in one heroic push but in tiny loops: one screen, run, click, fix, commit, repeat. You know there's a spectrum of ways to build, and the smart move is the simplest tool that does the job. And you've seen how a single feature only works when the whole chain is wired end to end. AI writes each piece fast; you name the layers, run the loop, and complete the chain. Next lesson: testing that app properly, shipping it to a real URL, and improving it once people use it.

  • Every app is three layers: UI (the screen), logic (the rules), data (what it remembers)
  • Build in tiny loops — one screen, run, click through, fix, commit, repeat
  • Pick the simplest approach that works; drop toward code only when forced
  • A feature is a chain — UI to logic to data to screen — and needs every link
  • Name the broken layer clearly and AI fixes it fast; "it doesn't work" fixes nothing
