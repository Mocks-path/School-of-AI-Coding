Week 3 · Lesson 04 · AI Agents

Trust an agent only as far as you've tested it.

An agent that dazzles in one demo can quietly fail one time in five — and you'd never know from a single run. Before you let one loose, you have to measure how reliable it actually is, plan for the ways it breaks, and decide exactly how much freedom it has earned. This lesson is about turning a clever demo into something you can actually depend on.

01 / 04

The same task, run twice, gives two answers

The first thing to unlearn: an agent is not a calculator. Run the identical task with the identical prompt ten times and you'll get ten slightly different runs — some perfect, some clumsy, the odd one wrong. This is non-determinism, and it's normal.

Because an agent's output varies run to run, a single successful demo tells you almost nothing. The honest way to measure reliability is to run the same task many times and look at the spread of outcomes — not one lucky result, but the whole cloud of them. A good evaluation isn't a single green checkmark; it's a range, with an average you can quote and a spread you can respect. One demo is a magic trick, not a measurement

The most expensive mistake with agents is trusting the demo. You run it once, it works beautifully, you ship it — and in production it fails one time in five on the same task, because that one perfect run was never the whole story. Professionals treat a single success the way a scientist treats a single data point: interesting, but meaningless alone. Run it many times, count the wins, and quote the rate — that number, not the demo, is the truth about your agent.

02 / 04

Turn many runs into one honest number

Once you accept that agents vary, evaluation becomes simple arithmetic: run the task N times, count how many succeed, and read the success rate. That percentage is the single most useful fact about any agent you're about to trust.

A success rate is just wins over attempts — but it moves with the task. A simple, clearly-worded, one-step job might pass 95+ times out of 100. Pile on complexity, a vague prompt and a long chain of steps, and the rate can collapse — because every extra step is another place to slip, and the failures multiply. Set the bar by the stakes

There's no universal "good enough" — the required success rate depends entirely on what a failure costs. An agent that drafts ideas for you to review can be gloriously unreliable; a mistake just gets deleted. An agent that touches money or sends things to real people needs to be far higher, and even then it needs a human check. Decide the bar before you measure, based on the damage a single failure could do — then hold the agent to it.

03 / 04

Every way it breaks has a guardrail

Agents fail in a small, predictable set of ways. The good news: each one has a standard guardrail that contains it. You don't prevent failure — you make sure that when it happens, it's cheap and caught.

A guardrail is a limit you place around the agent so a mistake can't spiral. Four failure modes cover most of the trouble: it invents a tool that doesn't exist, it gets stuck repeating itself, it grabs the wrong tool for the job, or it burns through cost with no ceiling. For each, there's a well-worn fix — a check, a cap, a clearer setup, a budget. Read the map below; this is the checklist that turns a risky agent into a safe one.

Figure 3 · Failure modes and the guardrail for each
Hallucinated tool call
What it looks like: the agent calls a tool that doesn't exist, or invents arguments it was never given.
● Hallucination

Guardrail: validate every call against a fixed schema and reject anything that doesn't match.

Infinite loop
What it looks like: the agent repeats the same step over and over, never deciding it's done.
◐ Runaway loop

Guardrail: cap the number of steps; stop after N turns and hand back to a human.

Wrong tool for the job
What it looks like: it reaches for the search tool when it should have used the calculator, or the reverse.
▲ Wrong tool

Guardrail: give few, well-scoped tools with clear descriptions, and log every choice.

Runaway cost
What it looks like: a long, looping task quietly runs up a huge bill in tokens or API calls.
● Cost blowout

Guardrail: set a hard budget per task and halt the moment it's hit.

Contain, don't just hope

Beginners try to make an agent that never fails and are perpetually disappointed. Builders assume it will fail and make sure the failure is boring — a capped loop that stops itself, a budget that trips before the bill hurts, a schema that rejects a hallucinated call before it does damage. Notice the pattern: every guardrail turns a potential disaster into a small, logged, recoverable event. That's the whole job — not perfection, but containment.

04 / 04

How much freedom has the agent earned?

The last decision before shipping isn't technical — it's about trust. For every action an agent can take, you answer one question: can this be undone? Reversible and read-only actions can run on their own; irreversible ones must wait for a human. Click around the ladder to see where the line falls.

Autonomy isn't all-or-nothing — it's decided action by action, on a simple test: the harder something is to undo, the more it needs a human first. A read-only lookup? Let it run. A reversible draft or label? Autonomous, but keep a log. Something that spends money or sends a message to a real person? Require your approval. Something truly irreversible — deleting for good, moving real funds? A human does that by hand. Click each rung to see who owns it and why.

Automate the safe, gate the dangerous

The goal of this whole week wasn't to build an agent you hand the keys to and walk away from — it's to build one you can trust because you know exactly where its freedom ends. Let it run free on everything read-only and reversible, where a mistake is cheap and undoable. Put a human gate in front of everything that spends, sends or can't be taken back. An agent on full autopilot will eventually make a confident, irreversible mistake. An agent that acts freely inside safe limits and asks before the dangerous moves is the one you can actually ship.

What to carry forward

An agent earns trust the way anything does — by being measured, not admired. Because it's non-deterministic, you judge it over many runs and quote a success rate, not a demo. You map each way it can break to the guardrail that contains it. And you hand it freedom in proportion to how reversible its actions are — free rein on the safe and undoable, a human gate on the irreversible. Do that, and a clever demo becomes something you can actually depend on.

  • Agents are non-deterministic — the same task varies every run
  • Measure reliability over many runs; a success rate beats a single demo
  • Every failure mode has a guardrail: schema check, step cap, scoped tools, budget cap
  • Set the required success rate by the cost of a failure
  • Decide autonomy by reversibility — automate the safe, gate the irreversible
