Match each app state to the moment it should show

A polished app doesn’t just have a "working" screen — it has a screen for every situation. The four states below (empty, loading, error, success) each belong to a specific moment. Beginners build only the success state and their app looks broken the rest of the time. Drag each state into the moment it should appear. Get all four right to finish.

The four app states

When does it show? — drag each here

💡 Design the whole story, not just the happy ending: what shows before any data arrives (empty)? While it’s fetching (loading)? When something goes wrong (error)? And when it works (success)? Ask AI to build all four states, then look at each one yourself. An app that only has a success screen feels broken the moment reality isn’t perfect.
2

Sort the shipping concepts — from your machine to the world

"It works on my computer" isn’t the same as "people can use it." Shipping means moving your app from your local machine to a hosted home on the internet — and handling config & secrets so nothing sensitive ends up in your code. Drag each idea into the group it belongs to. Wrong answers carry a hover hint.

Local (your machine)
Where you build & test · only you can see it
Hosted (live for users)
On the internet · anyone with the link can use it
Config & secrets
Kept out of code · different per environment
💡 The golden rule of shipping: secret keys and passwords never go in your code — they live in environment config that stays out of what you publish. And "works on my machine" only counts once it also works on the hosted version, where the settings can differ. AI can set most of this up for you; knowing what belongs where is how you keep it safe.
3

Walk the happy path, then pick the sad path to test

The happy path is when everything goes right — and it’s the one thing beginners test. Real users take sad paths: they leave fields blank, type the wrong thing, or lose their connection. Here’s the happy path for a sign-up form. Below it are four sad paths you could test next. Click the one that’s the highest-risk gap most worth testing first.

Happy path (already works) User opens the form → Types a valid name & email → Clicks Sign up → Sees "You’re in!"
Sad path to test Likely? Damage if it breaks
How to prioritize: test the sad path that is both likely to happen AND damaging when it does. A rare, harmless glitch can wait; a common mistake that lets bad or empty data through — or crashes the app — needs testing before you ship.
