Week 4 · Lesson 04 · AI Automation

Automations that keep working.

Building an automation is the easy part. Keeping it running — quietly, correctly, for months, while the apps around it change and the volume climbs — is the real skill. This final lesson is the unglamorous engineering that separates a demo from a system you can trust: knowing why flows break, handling errors on purpose, refusing to do the same thing twice, and seeing failures before your users do.

01 / 04

Why automations break

A flow that worked perfectly on Tuesday can quietly stop working on Wednesday — and the reasons are boringly predictable. Almost every failure is one of a handful of usual suspects. Learn to recognise them and you'll debug in minutes instead of hours.

The important shift in mindset: a working flow is not a finished flow. It runs in a world of other people's apps, networks, and limits, none of which asked your permission before changing. The goal isn't a flow that never fails — that doesn't exist — it's a flow that fails in ways you anticipated and handled.

Expect the failure, then handle it

Every one of these has a known answer, and the next three sections are those answers: retries and alerts for the temporary breaks, a de-dup check for the double-fire, and monitoring for the silent one. Naming the failure is ninety percent of fixing it.

02 / 04

Handle errors on purpose

When a step fails, the flow needs a plan — decided by you, in advance, not improvised by a machine at 3am. There are three good responses, and the whole art is matching the right one to the right kind of failure. Flip each card for when to reach for it.

The wrong instinct is to make everything retry, or to make everything stop and shout. Retrying a payment can charge someone twice; stopping for every network blip buries you in false alarms. Good error handling is a set of deliberate choices, one per risky step.

Retry with backoff

For temporary blips

A timeout, a brief rate limit, a network hiccup — these fix themselves. Don't give up; retry after a short wait, then a longer one, then longer still. Most transient errors vanish by the second try. Just cap the attempts so it can't loop forever.

Alert a human
When should you use it?
tap to flip
For judgement calls

Some failures aren't safe to retry — a payment, an ambiguous AI output, anything with real consequences. Stop, and send a clear alert with what broke and the data. A person decides. Automation that knows when to ask for help is the trustworthy kind.

Fail safe, not messy
When should you use it?
tap to flip
For anything that writes data

If a step can't finish, it should stop in a known-safe state: skip rather than half-write, keep the item for later, never leave data half-changed. A flow that fails cleanly can simply be re-run; one that fails messily corrupts what it touched.

Which one, when?
How do you choose?
tap to flip
Match response to failure

Temporary and reversible → retry with backoff. Consequential or ambiguous → alert a human. Anything that could corrupt data → fail safe first. Real flows use all three, at different steps. Decide the response before the failure, not during it.

A retry cap and an alert path

Two settings turn a fragile flow into a resilient one: a limit on how many times a step may retry (so a permanent error doesn't loop forever), and a place your alerts actually land — a channel a human reads, not a folder nobody opens. Set both once and every future step inherits a safety net.

03 / 04

Do it once, even when the trigger fires twice

Remember the very first failure: a trigger that double-fires. It's so common it has its own solution, and its own intimidating word — idempotency. It only means this: running the same thing twice should have the same effect as running it once. No double charges, no duplicate messages.

The danger is real. Webhooks retry when they're unsure you received them; polling windows overlap; a user double-clicks. Any of these can hand your flow the same event twice, a second apart. Without a guard, the flow dutifully does everything twice. The fix is a small, deliberate de-dup check — and it's the difference between an automation you trust with real actions and one you have to babysit.

The guard — act exactly once
1 · Give each event an ID
Every event carries a unique key — here, #A17. That key is how the flow will recognise a repeat later.
2 · Check before you act
Before doing any work, the flow asks: "have I already handled #A17?" It looks the key up in a small list of what it has processed.
3 · Act once, record it
First time: do the work, then store the key. Second time: the key is already there, so the flow skips. One event, one action — that's idempotency.

The key you already have

You rarely need to invent an ID — the data usually carries one: an order number, a message ID, a row's unique reference. Store the ones you've handled, check against that store before acting, and a double-fire becomes a harmless no-op. This one small habit is what makes it safe to automate actions that actually matter.

04 / 04

Monitoring: catch the failure you never see

The worst failure isn't the loud one that crashes and emails you an error. It's the silent one: a step quietly stops working, the flow reports success, and everything looks fine — until days later you discover nothing has actually run. You can't fix what you can't see. Monitoring is how you see.

Three simple habits give you eyes. Logs record what each run did, so you can look back. Alerts ping a human the moment something errors, so you don't have to watch. And a heartbeat — the clever one — expects the flow to check in on schedule; if the 9am run simply never happens, the missing heartbeat raises the alarm. That last one is the only thing that catches a flow that failed by not running at all.

Scale is just reliability, repeated

Scaling an automation isn't about doing something clever — it's about doing the boring things above, everywhere. Every new flow gets error handling, a de-dup guard, and monitoring from day one. Ten flows you can see beat a hundred you can't. Build each one to fail safely and report loudly, and growth stops being scary.

Week 4 · What you carry forward

You can build an automation — now you can keep it alive. Failures are predictable: fields change, triggers double-fire, rate limits bite, AI steps return junk, and the worst ones fail silently. Handle each on purpose — retry the blips, alert a human for judgement calls, fail safe when data is at stake. Guard against double-fires with a de-dup check. And see everything with logs, alerts, and a heartbeat. Reliability, repeated, is what scaling actually means.

  • Retry with backoff · alert a human · fail safe — match it to the risk
  • Idempotency: give events an ID, check before acting, do it once
