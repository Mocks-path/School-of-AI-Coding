Beat One · Think in Automations

The Chore That Repeats Itself — Meet the Automation

Before Maya builds anything, one realisation reframes the whole week: last week's job needed judgment every time, so it needed an agent. This week's job is the opposite — it happens the exact same way on every booking. Spotting that a chore is a trigger → steps pipeline — and that an automation, not an agent, is the right tool — is the first beat.

📖 The story so far Monday, 7:40 a.m. Another workshop booking lands overnight. Maya knows the drill by heart: open the booking, read who it's from, copy the name, date, party size and any notes into her workshop spreadsheet, then message the host to prep. Then the same again for the next booking, and the next. She's done this little three-app shuffle hundreds of times. Her instinct from Week 3 kicks in — build an agent. Then she stops: an agent decides what to do; here I already know every step, and they never change. This isn't an agent problem. It's her first automation.

Beat Two · Design It

Map It First — Trigger, Steps, Fields, and the Human Checkpoint

An automation is only as good as the map you draw before you build. Maya writes a one-page blueprint: the trigger that starts it, the steps in order, the exact data fields she's moving, where an AI step handles the messy bit — and, most important, the error path and the one place a human approves. A vague map makes a fragile, silently-broken workflow.

📖 The story so far Tuesday evening. Maya has decided: this chore is worth automating. But she remembers the lesson from InboxScout — design is cheap on paper and expensive later. So before she opens any builder, she writes BookingBridge's blueprint. The same workflow can be a dependable little machine or a fragile mess depending entirely on how clearly she maps it. Flip between three versions of the blueprint below and watch the whole thing change character.
📄 bookingbridge / blueprint.md

BookingBridgeAutomation blueprint · draft
Trigger: a new workshop booking arrives → steps: read it, AI-extract the details, save a tidy row, notify the host — pause for me before anything charges money.
Fields: name, date, party size, notes → columns in the workshop sheet. AI step: turn the free-text booking into those clean fields. Error path: if a field is missing or the text can't be parsed, don't save a broken row — flag it for me. Approval: any booking that takes payment waits for my OK.

"When a booking comes in, just sort it out and put it wherever it needs to go. Handle whatever's needed."
← This is a wish, not a blueprint. No named trigger, no ordered steps, no list of fields, and no plan for when something's missing — which is exactly how a workflow silently saves half-empty rows and nobody notices for a week. Vague map in, fragile automation out.
"Trigger: new booking. Steps: 1) read the booking, 2) AI-extract name/date/party size/notes, 3) save one row to the sheet, 4) message the host. If a field is missing → don't save, flag me. If it takes payment → pause for my approval."
← Same chore. The difference is the map: a concrete trigger, ordered steps, the exact fields being moved, an error path for the messy case, and one clear human checkpoint. This is what you design before you build anything.

Maya's design checklist

  • Name the  trigger  and what "done well" looks like (success criteria)
  • List the  steps  in order — read → AI-extract → save → notify
  • Map the data fields (name, date, party size, notes → sheet columns)
  • Decide where the AI step goes (reading the messy free-text booking)
  • Design the error path (missing field or unreadable text → flag, don't save)
  • Add the human approval checkpoint (any step that takes money pauses for Maya)
✅ BookingBridge's blueprint is written. One page: trigger, steps, fields, AI step, error path, approval checkpoint. Maya hasn't built a thing yet — and that's exactly why the build will go fast. Onto the workbench.

🎚️ The Approval Dial — which steps run alone, which pause for a human?

The single most important design choice: not what can the automation do, but which steps may run without a human. The rule of thumb — let it act alone on cheap, reversible steps; keep a human checkpoint on anything that touches money or can't be undone. Pick a step and see where it lands.

💡 Approval isn't all-or-nothing — you set it step by step. A saved row you can edit; a charged card you can't quietly take back. Start tight: let it run alone only where a mistake is cheap and reversible, and widen the leash later once the numbers say it's earned it.

Beat Three · Build It

One Step at a Time — Test With Real Sample Data

Now Maya builds — but not all at once. She picks a low-friction builder, adds one step at a time, and tests each with a real past booking before adding the next. The tricky part is the AI step: it must return the details in a required format the next step can actually use. The superpower here is the run log: every step shows its input and output, so when something breaks — a bad field mapping, junk from the AI — you can see exactly where.

📖 The story so far Wednesday. Maya opens a low-code automation builder — the kind where you drag steps into a row and connect a trigger without installing anything. She resists wiring up all four steps at once. Instead: get the trigger firing first, test; add the AI-extract step, test; add the save-to-sheet step, test; then the notify step. After each step she runs it on a real booking from last month and reads the output line by line. Because that's the whole game — an automation that isn't tested on real data fails on the first weird booking. Below is one test run's log. Judge each step.

Beat Four · Reliability

It Has to Run Unattended — De-dup, Alert, Monitor, Then Ship

An automation that worked in the demo hasn't earned the right to run while you sleep. Maya runs BookingBridge on many bookings, hunts for the silent failure — the run that quietly did nothing, or fired twice — then adds the three things every unattended workflow needs: a de-dup key, an error alert, and monitoring. Only then does she ship it — documented, with a human on anything that touches money.

📖 The story so far Thursday. BookingBridge runs. But Maya doesn't trust it because one demo looked clean — she remembers that a workflow which works once isn't shipped. Two things scare her most: the run that fails silently (a booking never reached the sheet and nobody noticed for days), and the trigger that double-fires (the same booking saved twice). So she replays 30 real bookings, counts what slipped, and decides — for each behaviour — retry, alert a human, or fix it first. Play with the reliability numbers, then judge each behaviour.

Reliability nets added

BookingBridge ships — but on Maya's terms. It saves and notifies on its own, because that's cheap and easy to fix. It never charges a card without her nod, because that can't be undone. And before it went live she added the three nets every unattended workflow needs: a de-dup key so a double-fire can't save the same booking twice, an error alert to her phone the instant a run fails, and a monitoring log she can glance at. Transient hiccup? It retries, then alerts. She didn't build a magic robot — she built a boring, dependable, documented workflow that gives her back the swivel-chair hour and pings her only when a human is actually needed. That's the difference between hype and a shipped automation. 🎉

The Honest Beat

Hype vs Durable — What an Automation Actually Is

Before you celebrate, the slide most courses skip. The internet is loud with "set it and forget it, fully hands-off." Know exactly what automations genuinely changed — and what they never will.

⚖️ The Durable / Hype Split

Build your instincts on the left column. Ignore anyone selling you the right one.

✓ What automations genuinely changed
  • A repetitive, same-shape chore can now run itself, tirelessly, on every trigger
  • An AI step can read the messy free-text part that used to need a human
  • The three-app swivel-chair shuffle collapses into one reliable pipeline
  • One person can hand off real busywork — and monitor it instead of doing it
✕ What automations did NOT change (the hype)
  • They still fail — often silently, until someone notices the missing rows
  • "Set it and forget it, never check it" is marketing, not reality
  • A vague map still produces a fragile, half-broken workflow
  • Nothing replaces your judgment on the money-touching, irreversible step
