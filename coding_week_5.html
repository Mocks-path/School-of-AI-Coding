Beat One · What's an API

Every AI Feature Is "Just" an API Call — Request, Response, JSON

Before Maya builds anything, one realisation reframes the whole week: the fancy AI feature she wants — read a messy customer request and draft a tidy reply — isn't something she has to invent or host. It already exists behind an API: she sends a request, she gets a response back (usually as JSON), and that's the whole trick. Learning to picture that request→response loop, and reading the docs to pick the right API, is the first beat.

📖 The story so far Monday, 8:10 a.m. Maya sketches her capstone: a little intake box where a customer types "hey, want to book a candle night for my sister's hen do, maybe 8 of us, something calming" — and something reads that mush and hands her back a clean summary and a warm draft reply. Her first instinct is panic: I'd have to build an AI for that. Then she remembers the whole point of this week. No — I don't build the model. I call one. Somebody already runs the model; they expose a door called an API; she sends text in, she gets structured text back. Her job isn't to be a scientist. It's to make one good phone call and use the answer well.
🏭
Build & run your own model · Rarely right

Host your own AI model

Train or run a large model yourself on your own machines. Enormous cost, deep expertise, and months of work — the answer for a handful of big labs, and almost never the answer for a builder who just wants a feature. Reaching here first is the classic beginner over-reach.

🔌
Call a model someone else runs · The fit

Call an AI API

Send a request (your prompt + a few settings) to a model someone else already runs; get a response back, usually as JSON, in a second or two. You pay per use, you skip all the hosting, and you wire the answer into your own app. This is how nearly every AI feature you've ever used is actually built.

Beat Two · The First Call

Make the First Call — Key, Model, Prompt, Params — and Keep the Key Safe

Now Maya makes a real call. Four things go into it: an API key (proves it's her account and gets billed), a model (which brain answers), a prompt (what she's asking), and a few params (settings like how long and how creative the answer is). Then she reads the response and watches the token cost. The one thing that can burn her: where she puts the key. A key in the browser is a key anyone can steal — it belongs on a server, not in code the whole world can view.

📖 The story so far Tuesday evening. Maya makes CandleConcierge's very first API call — and it works. A messy sentence goes in; a clean summary comes back as JSON. She almost celebrates by pasting her key straight into the web page so the browser can call the model directly. Then a chill: if the key is in the page, anyone who opens "view source" can read it — and run up my bill. So she moves the key behind a small server of her own; the browser talks to her server, and only her server holds the key. Flip between three ways she could wire it up below and watch a working feature turn into a security hole — or a safe one.

🔐 The Safety Dial — where does each piece of your API setup belong?

The most important choice in a first call isn't the prompt — it's what's allowed to touch the browser. Public things (the model name, the prompt template) are fine anywhere; the key and anything that spends money must stay server-side. Pick a piece and see where it lives.

💡 Rule of thumb: if leaking it would let a stranger spend your money, it goes on the server behind a secret. Everything else can be public. Treat your key like a password you can never un-share once it's out.

Beat Three · Build With APIs

Chain the Calls — Ask for Structured Output, Validate It, Survive Failures

One call is a party trick; a build chains calls into something useful — extract the details in one call, draft the reply in the next. Two hard truths make or break it. First: an AI response is text, so you must ask for a structured output (clean, labelled fields) and validate it before the next step trusts it. Second: calls fail — a 429 (too many requests) or a timeout — so you add retry with backoff and a fail-safe for when it still won't answer.

📖 The story so far Wednesday. Maya chains two calls: call one turns the customer's mush into structured fields; call two writes a warm draft reply from those fields. She resists trusting the output blindly — the model answers in text, and text lies about being tidy. So she demands a strict format, checks it matches before moving on, and decides what happens when a call errors instead of pretending it never will. 🔬 Read the run log — good step or bug?

For each thing CandleConcierge does, decide: ship it (the step is working) or debug it (something's wrong and needs fixing). Reading an API run against real data like this is the skill of building with APIs.

Draft call · validationThe draft call returns a warm, on-brand reply that fills in the missing name politely ("Hi there!") and confirms the mild-scent note. The output matches the required format and passes validation before it's shown to Maya.
Extract call · outputOn the next message, the extract call replies with a chatty paragraph — "Sure! It sounds like they'd like to book…" — instead of the strict structure. The code assumes clean fields, so it grabs junk and the party size comes through as the word "eight" in the date slot.
Call fails · 429A burst of five messages arrives at once. The model returns 429 — too many requests on three of them. The code has no retry, so it crashes and three customers get nothing back, silently.
Fail-safe pathA call times out twice, retries with a short back-off, times out again — so CandleConcierge stops retrying, saves the raw message, and flags it for Maya to answer by hand rather than sending a half-built reply.

The Finale · The Honest Beat

Hype vs Durable — What an AI API Actually Gives You

Before the celebration, the slide most courses skip. The internet is loud with "just plug in the AI and everything works, free and forever." Know exactly what an API genuinely changed for you — and what it never will — because that honesty is the difference between a builder and a buyer.

⚖️ The Durable / Hype Split

Build your instincts on the left column. Ignore anyone selling you the right one.

✓ What an AI API genuinely changed
  • You can add a real AI feature to anything you build — without training or hosting a model
  • A messy human message can become clean, structured fields your code can use
  • One person can wire a model's brain into a script, an app, or an automation with a single call
  • You pay per use and can watch the cost — no giant upfront bill to experiment
✕ What an AI API did NOT change (the hype)
  • It isn't free or limitless — every call costs tokens and can be rate-limited or time out
  • The output is text that looks tidy — you still have to require a format and validate it
  • A leaked key is a real, expensive risk; "just put it in the app" is how bills explode
  • Nothing replaces your judgment on the money-touching, irreversible step
