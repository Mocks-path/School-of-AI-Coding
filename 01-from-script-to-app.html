Week 2 · Lesson 01 · AI App Development

From a script to a real app.

In Week 1 you wrote scripts — little programs that run once, on your machine, for you. An app is different. It keeps running, other people use it, and it remembers things between visits. That jump feels enormous, but it comes down to understanding a few durable parts and how they fit together. This lesson gives you the honest map of what an app actually is, before you build one.

01 / 04

A script runs once. An app keeps running.

A script is a task you run and walk away from — clean up a file, crunch some numbers, print an answer. An app is something other people open, again and again, that remembers what happened last time. Same language, same logic — but a completely different shape of work.

Picture the scripts from last week: you double-click, it does its job in your terminal, it ends. Only you ever see it, and the moment it finishes it forgets everything. That's perfect for a one-off chore, and most useful programs start life exactly there. The gap opens when you want a second person to use it, from their own device, and to still see their data tomorrow.

An app closes that gap. It waits for a request, does the work, sends back a result, and stores anything worth keeping — then waits for the next person. Nothing about the logic got harder; what got added is an interface so others can reach it and a place to remember. What "an app" really adds

Notice what appeared that a script never had: a screen the user actually touches, and a place that remembers after the program stops. A script is logic alone. An app wraps that same logic in a way to reach it and a way to keep results — so a stranger on the other side of the world can use it tomorrow and still find their work. That's the whole difference: runs-once-for-you becomes keeps-running-for-everyone. And, reassuringly, the logic in the middle is the same skill you already started building.

02 / 04

The anatomy of an app: four connected parts

Every app you'll ever build — a to-do list, a booking tool, a whole social network — is made of the same four parts working together: an interface, some logic, a place for data, and a sense of state. Learn these four once and every app stops looking mysterious.

People imagine an app is one big magical thing. It isn't. It's four cooperating pieces, and you can point to each of them. The interface is what the user sees and taps. The logic is the rules that decide what happens when they do. The data is the information the app keeps. And state is the app's short-term memory of "what's going on right now" — which screen you're on, whether you're logged in, what's in your cart. How the four hand off

Watch the loop and it clicks: the interface catches a tap and hands it to the logic; the logic decides what to do and may read or write the data; then it updates the state so the interface can redraw the right screen. Round and round, every time anyone touches the app. You don't need to memorise a hundred concepts — you need to know which of these four parts a given problem belongs to. That single habit is what turns "build an app" from overwhelming into a sorting task.

03 / 04

Front-end and back-end: the storefront and the kitchen

Those four parts split naturally into two halves. The front-end is everything the user sees and touches — the storefront. The back-end is everything that happens out of sight — the kitchen. Knowing which half a task lives in tells you where to look when something needs building or fixing.

Think of a restaurant. The dining room — the menu, the tables, the waiter taking your order — is the front-end: polished, friendly, the only part the guest ever sees. The kitchen — the recipes, the pantry, the chefs — is the back-end: hidden, but where the real cooking and the ingredient storage happen. An app works exactly the same way. Why the split matters to a beginner

You don't have to master both halves at once. Many first apps are almost entirely front-end — a page that reacts to clicks with a bit of logic — and store their data in the browser itself. Others are a thin front-end sitting on a busy back-end. The value of the storefront/kitchen picture is that when you describe what you want to an AI assistant, you can say where the change belongs: "add a button" is dining-room work; "remember this after I close the tab" is kitchen work. That vocabulary alone makes you far easier to help.

04 / 04

Script, spreadsheet, automation, or app?

Not every problem deserves an app. Sometimes a spreadsheet is the honest answer; sometimes a one-line automation beats a week of building. The skill that saves the most time isn't coding — it's choosing the right shape of tool before you build anything. Flip each card to match a situation to its best tool.

The eager beginner reaches for "build an app" every time, and quietly wastes weeks. A seasoned builder asks first: how many people use this, does it need to remember things, and how often does it run? Those three questions usually reveal that a script, a spreadsheet, or a ready-made automation would solve the problem in an afternoon. An app is the heaviest tool in the box — reach for it only when the lighter ones genuinely can't do the job. Flip the four situations below to see which tool actually fits.

Multiple users, their own accounts, data that persists per person — now you need an app. Interface, logic, data and state all pull their weight here. This is the situation the heavy tool was made for, and where the rest of this week points.

The one-question decision

Before you build anything, ask the blunt version: "Do other people need to use this, and does it need to remember things between visits?" If the answer to both is yes, you're looking at an app. If it's no, a lighter tool almost always wins — a script, a sheet, or an automation you can wire up in an afternoon. Choosing the right shape first is the most valuable habit in this whole course; the AI can build any of them, but only you decide which one the problem deserves.

The one-sentence version

An app is a script that grew an interface so others can reach it and a memory so it never forgets — built from four parts (interface, logic, data, state) split across a front-end storefront and a back-end kitchen — and worth building only when many people need in and things must be remembered.

What to carry forward

You now know what separates an app from a script and the durable parts every app is made of. A script runs once for you; an app keeps running for everyone and remembers. Under the hood, every app is the same four parts — interface, logic, data, state — split into a front-end storefront and a back-end kitchen. And the most valuable move happens before you build: choosing whether the problem even needs an app, or whether a script, sheet or automation wins.
