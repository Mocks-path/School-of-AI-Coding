Week 3 · Lesson 03 · AI Agents

Build your first agent, one tool at a time.

An agent is a model that can think, use a tool, look at the result, and decide what to do next — over and over — until a task is done. This lesson shows you the surfaces you can build one on, the tiny loop you follow to grow it safely, and how to read the reasoning trace so you always know what your agent is actually doing.

01 / 04

You don't need to code to build an agent

There isn't one way to build an agent — there's a spectrum, from click-together builders to full code frameworks. More power costs more setup. Your job is to start at the simplest surface that can do the job.

Think of it as four rungs on a ladder. At the bottom, a no-code builder lets you assemble an agent by clicking and writing plain instructions. One rung up, an assistant platform gives you a ready-made agent you extend with your own knowledge and a few tools. Higher still, visual automation tools let you wire agent steps into a larger flow of triggers and actions. At the top, a code framework hands you total control over every step — and asks you to write real code for it. Reveal each rung below, then see how to pick your starting point.

Figure 1 · The build-approach spectrum
●○○○No-code agent builder Least code · fastest start

●●○○Assistant / chatbot platform Low code · guided

●●●○Visual automation with agent steps Some logic · wired flows

●●●●Code framework Most code · most control

Write the agent in code, defining each tool, every guardrail and how the reasoning loop runs. Nothing is hidden and nothing is decided for you.

Best forAgents inside your own product, custom tools, and precise control over each step.

How to choose your starting point

Least code

A no-code builder. If you can describe the task in words, you can ship a first agent today.

Most control

A code framework — but only reach for it when a simpler surface genuinely can't do the job.

Rule of thumb

Start one rung lower than you think you need. You can always climb; you rarely need to.

The trap

Picking a framework because it sounds serious — then losing a week to setup a no-code tool would have skipped.

Climb only when you hit a wall

Every rung up the ladder buys you more control and charges you more time. Beginners routinely overpay — they reach for a code framework to build something a click-together tool would have finished by lunch. The honest move is to start at the simplest surface that could plausibly work, and climb only when you hit a real limit: a tool that doesn't exist yet, a step you must control exactly, or a system you need the agent to live inside. The tools named here are only examples of each category — new ones appear constantly. What lasts is the ladder itself.

Watch an agent think, step by step

The idea on paper is tidy. The reality is a running trace: thought, tool call, observation, next step — looping until the job is done. Learning to read that trace is the single most useful skill you'll build this week.

An agent isn't magic and it isn't a single answer. It works in a visible loop: it writes a thought about what to do, makes a tool call with an exact input, reads the observation that comes back, and decides the next step — often looping again. Play the trace below and follow the panel on the right. When something goes wrong later, this trace is exactly where you'll look to find out why.

The trace is your debugger

When an agent does something baffling, the trace tells you exactly where it went off the rails — a wrong thought, a tool called with a bad input, or an observation it misread. Beginners treat the agent as a black box and get frustrated; builders open the trace and read it like a story. Notice the loop in the example: search, then write, then finish. Most real tasks are just that same thought → tool → observation → next-step cycle, repeated until the goal is met.

03 / 04

Grow the agent one tool at a time

The mistake is to hand a new agent five tools and a wall of instructions and hope. The discipline is a tiny loop: start with clear instructions and ONE tool, test, and only add the next tool once the last one works.

Every reliable agent is grown, not born. You begin with the smallest thing that could work — plain instructions and a single tool — and give it a real task to try. If it passes, you add one more tool and test again. If it fails, you fix one thing and re-test before adding anything. This keeps every problem small and findable: when something breaks, you know it was the last thing you changed. Watch both outcomes below.

Small loops make problems findable

The whole point of adding one tool at a time is debuggability. If you bolt on five tools at once and the agent misbehaves, you have no idea which one caused it. Add them one by one, test after each, and every failure points straight at its cause — the thing you just changed. It feels slower for the first hour and saves you days by the end. Reliable agents come from small, boring, repeated loops, not from one heroic setup.

Simplest-that-works is a discipline, not a limitation

Choosing the simplest surface that can do the job isn't settling — it's how you ship this week instead of next month. A framework you don't need is a week of setup you didn't have to spend. Reserve that power for the projects that genuinely require it: agents inside your own product, custom tools, or control over every step. For everything else, the click-together surface wins — not because it's fancier, but because it gets a working agent in front of you today, where you can actually learn from it.

What to carry forward

Building an agent isn't one skill — it's three habits. Pick the simplest surface on the spectrum that can do the job. Grow the agent one tool at a time, testing after every change. And read the reasoning trace so you always know what it's actually doing. Do those three and you'll ship agents that work — and know exactly why when they don't.

  • Building runs a spectrum: no-code → assistant platform → visual automation → code framework
  • Start one rung simpler than you think you need; climb only when you hit a wall
  • Grow it one tool at a time — test after every change so failures stay findable
  • Every agent runs a loop: thought → tool call → observation → next step
  • The reasoning trace is your debugger — read it like a story
