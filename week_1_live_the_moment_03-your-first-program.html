Your First Real Program — write it, run it, read the error, fix it

Five hands-on drills. Pick a low-friction place to write code for each scenario, put the build loop in the order that actually works, learn to read an error message instead of fearing it, assemble a debugging request an AI can actually act on, and diagnose what broke in five short snippets.

Pick the lowest-friction place to write it

Where you write code matters less than that you run it today. The goal for a first program is fewest steps between an idea and a working result — no hour lost to installing things. Put the build loop in the order that works

Beginners try to write a whole program, then run it once at the end and drown in errors. Experienced builders run a tiny loop, over and over, so a mistake is caught while it is still small. Read the error — what does it mean, what do you do?

An error message is not the program yelling at you — it is the program telling you where it got stuck and why. Almost every message names a type, a location, and a cause. Read three real-shaped errors below. For each, click the reading that correctly says what it means and what to do next; you get the verdict instantly.

Assemble a debugging request an AI can actually fix

"It's broken, fix it" wastes everyone's time — the AI has to guess, and it guesses wrong. A good debugging request gives it the three things it needs to reason: what you ran, what happened, and what you wanted instead. Drag each item into Include or Leave out. "What broke?" — read the snippet, find the bug

You don't need to memorise a language to reason about a bug — you need to read carefully and ask "what did I expect versus what would this actually do?" Five short snippets, each with one thing wrong. Pick the real cause, then submit for a per-question review.
