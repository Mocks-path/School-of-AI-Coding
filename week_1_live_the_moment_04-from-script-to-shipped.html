1

Place each project on the ladder

Not everything needs to be "production software." A script runs once, for you. A tool runs many times, still mostly for you or your team. A product runs for strangers who will never see your code — and that raises the bar on reliability, safety, and polish. Knowing which rung you are on tells you how much testing and hardening is actually worth it. Match each project to its rung, then check.

2

Order the version-control save-points

Version control is just save-points for code — each "commit" is a labelled snapshot you can return to if the next change breaks everything. The skill is committing at the right moments: a good history is a series of small, working states, each with a clear message. Click the five save-points in the order a careful builder makes them — a wrong click gets you a nudge. Project: adding a "download as CSV" button to your tool.

What should you test — and what's the missing edge case?

"It worked when I tried it" tests one path: the happy one, with tidy input. Real users feed programs empty fields, huge numbers, weird characters, and zero. A test is just a promise you check on purpose — "given this input, I expect this output." For each function below, pick the input most likely to break it: the edge case you forgot.

Trust vs. verify — green flags and red flags in AI code

AI writes plausible code fast — and "plausible" is exactly the danger, because plausible-looking code can still be wrong or unsafe. Your job is to know what to accept and what to stop and check. Drag each item into Green flag — safe to trust or Red flag — stop and verify. Hover any red pill for the correction.
